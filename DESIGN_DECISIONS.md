## Решения

### <a id="d-01"></a>D-01. Своими заявками участник управляет по клиентскому ID; участник определяется по сессии

**Контекст:** у каждой заявки есть биржевой ID, и он виден всем в публичном потоке — без него подписчики не смогут построить стакан. Если команды отмены и изменения принимают биржевой ID, любой трейдер может указать в них чужую заявку, и её защищает только проверка владельца ([T-01](THREAT_MODEL.md#t-01)). Кроме того, приватный отчёт может уйти не тому участнику ([T-04](THREAT_MODEL.md#t-04)), а публичный поток — выдать владельца заявки ([T-05](THREAT_MODEL.md#t-05)).

**Решение:**

1. У каждой заявки два идентификатора с разным назначением:

   | | Клиентский ID | Биржевой ID |
   | --- | --- | --- |
   | Кто назначает | Участник, при отправке заявки | Биржа, при приёме заявки |
   | Уникален | Среди заявок одного участника | Среди всех заявок биржи |
   | Кто его видит | Только владелец | Владелец и все подписчики публичного потока |
   | Для чего | Управлять своей заявкой | Наблюдать за стаканом |

2. Участник определяется при входе и закрепляется за сессией. В командах клиента поля «участник» нет — его добавляет gateway.
3. Команды клиента (`NEW_ORDER`, `CANCEL`, `REPLACE`) содержат только клиентский ID. Биржевой ID не принимает ни одна команда: он только выходит из биржи, но никогда не приходит в неё.

```
   Клиент A → биржа:      NEW_ORDER  клиентский ID 42, покупка 500 по 100.00
   Биржа → A (приватно):  заявка 42 принята, биржевой ID 900517
   Биржа → все (публично): добавлена заявка 900517, покупка 500 по 100.00
   Клиент A → биржа:      CANCEL  клиентский ID 42
```

4. Ядро ищет заявку по паре «участник из сессии + клиентский ID». Заявки других участников в поиск не попадают. Если заявка не найдена, ответ — «заявка не найдена», одинаковый для чужой и несуществующей.
5. `REPLACE` содержит старый клиентский ID заявки и новый, под которым изменённая заявка известна дальше.
6. Приватный отчёт отправляется только в текущую сессию владельца и содержит оба ID своей заявки, но ничего о контрагенте. Если владелец не подключён, отчёт не отправляется никому.
7. Публичное событие содержит только биржевой ID — без владельца, клиентского ID и сессии. Биржевой ID берётся из одного общего счётчика биржи и не содержит номера участника.
8. Разрешённые типы команд зависят от роли сессии. Gateway проверяет их при приёме, ядро — повторно перед исполнением.

**Обоснование:** знание чужого биржевого ID ничего не даёт: ни в одной команде нет поля, куда его можно подставить. Проверка владельца совпадает с поиском заявки, поэтому ответ на чужую и несуществующую заявку одинаков без дополнительных усилий. Клиентский ID удобен и для самого участника: он известен сразу при отправке, поэтому маркет-мейкер может отменить или изменить заявку, не дожидаясь подтверждения биржи. Так устроен протокол Nasdaq OUCH. Альтернатива — принимать в командах биржевой ID и сравнивать владельца заявки с участником из сессии, как в CME iLink. Она проще в реализации, но не позволяет управлять заявкой до подтверждения и требует отдельно следить, чтобы отказ по чужой заявке не отличался от отказа по несуществующей.

**Связанные угрозы:** [T-01](THREAT_MODEL.md#t-01); также [T-04](THREAT_MODEL.md#t-04), [T-05](THREAT_MODEL.md#t-05).

**Связанные требования:** [SR-01](SECURITY_REQUIREMENTS.md#sr-01); также [SR-02](SECURITY_REQUIREMENTS.md#sr-02), [SR-03](SECURITY_REQUIREMENTS.md#sr-03), [SR-04](SECURITY_REQUIREMENTS.md#sr-04).

**Будущая проверка:** критерии приёмки [SR-01](SECURITY_REQUIREMENTS.md#sr-01)…[SR-04](SECURITY_REQUIREMENTS.md#sr-04), а также:

1. **Чужой биржевой ID бесполезен.**
   - **Условие:** у A заявка с клиентским ID 42 и биржевым ID `X`; у B заявки 42 нет.
   - **Действие:** B отправляет `CANCEL` и `REPLACE` с клиентским ID 42, затем с числом `X` в поле клиентского ID.
   - **Ожидаемый результат:** во всех случаях «заявка не найдена»; заявка A не изменилась.
2. **Одинаковые клиентские ID у разных участников.**
   - **Условие:** у A и у B есть заявки с клиентским ID 42.
   - **Действие:** B отменяет заявку 42.
   - **Ожидаемый результат:** снята заявка B, заявка A на месте.
3. **Случайные последовательности.**
   - **Условие:** случайные команды нескольких участников; эталонная реализация из тестового контура.
   - **Действие:** после каждой команды проверяется, чьи заявки изменились.
   - **Ожидаемый результат:** ни одна команда не изменила чужую заявку.
4. **Роли.**
   - **Условие:** сессии трейдера, наблюдателя и администратора.
   - **Действие:** каждая сессия отправляет все типы команд; трейдер пытается войти на административный вход, администратор — на торговый.
   - **Ожидаемый результат:** исполнено только то, что разрешено роли; остальное отклонено без изменения состояния.

**Ограничения и последствия:** решение не защищает при краже учётных данных участника. Клиент должен помнить клиентские ID своих заявок; потеряв их, он запрашивает список своих активных заявок, где указаны оба ID. Администратор видит владельцев заявок в журнале, но не может торговать ([SR-02](SECURITY_REQUIREMENTS.md#sr-02)), а его действия записываются ([SR-09](SECURITY_REQUIREMENTS.md#sr-09)).

### <a id="d-02"></a>D-02. Формат сообщений проверяет gateway, лимиты — ядро

**Контекст:** ядро одно и работает в одном потоке. Если команда его уронит, торги остановятся у всех, а при восстановлении из журнала ядро упадёт на ней снова ([T-02](THREAT_MODEL.md#t-02)). Кроме того, лимиты участника нельзя обходить ([SR-06](SECURITY_REQUIREMENTS.md#sr-06)), а здесь есть три лазейки:

- gateway многопоточный и видит состояние торгов с опозданием, поэтому две одновременные заявки могут обе пройти лимит числа заявок;
- `REPLACE` может увеличить уже принятую заявку сверх лимита;
- коридор, отсчитываемый от цены последней сделки, участники могут сдвинуть своими сделками.

**Решение:**

1. Gateway проверяет всё, что не зависит от состояния торгов: длину, тип и поля сообщения; что цена и объём положительны, кратны шагу цены и лоту и не выше предельных значений; что инструмент существует; частоту сообщений. Сообщение неверной длины разрывает сессию.
2. Ядро проверяет всё остальное одной функцией — и для `NEW_ORDER`, и для `REPLACE`: торги открыты; участник не заблокирован; новый клиентский ID больше предыдущего; объём и цена в пределах лимитов; открытых заявок меньше лимита. Если `REPLACE` отклонён, заявка не меняется.
3. На любую команду ядро отвечает исполнением или отказом, но не падает: все вычисления проверяют переполнение.
4. Ценовой коридор задаётся при открытии торгов и меняется только администратором.

**Обоснование:** до ядра доходят только корректные по формату команды, а ядро на них не падает. Значит, не упадёт и восстановление из журнала ([SR-05](SECURITY_REQUIREMENTS.md#sr-05)). Ядро исполняет команды строго по одной, поэтому «проверить лимит и добавить заявку» в нём — одно действие, и гонки нет. Одна функция для всех команд закрывает обход через `REPLACE`. Альтернатива — проверять лимиты в gateway. Ответ приходил бы быстрее, но осталась бы гонка, а результат нельзя было бы воспроизвести по журналу.

**Связанные угрозы:** [T-02](THREAT_MODEL.md#t-02); частично [T-03](THREAT_MODEL.md#t-03) (лимит частоты).

**Связанные требования:** [SR-05](SECURITY_REQUIREMENTS.md#sr-05), [SR-06](SECURITY_REQUIREMENTS.md#sr-06); поддерживает [SR-09](SECURITY_REQUIREMENTS.md#sr-09).

**Будущая проверка:** критерии приёмки [SR-05](SECURITY_REQUIREMENTS.md#sr-05) и [SR-06](SECURITY_REQUIREMENTS.md#sr-06), а также:

1. **Фаззинг.**
   - **Условие:** фаззер подаёт в gateway случайные байты, а в ядро — команды с крайними значениями; параллельно торгует B.
   - **Действие:** долгий прогон с проверкой инвариантов из [§8 паспорта](PROJECT.md#sec-8) после каждой команды.
   - **Ожидаемый результат:** биржа не падает, инварианты соблюдены, заявки B исполняются.
2. **Восстановление после фаззинга.**
   - **Условие:** журналы фаззинг-прогонов.
   - **Действие:** восстановление по каждому журналу.
   - **Ожидаемый результат:** восстановление проходит, состояние совпадает с исходным.
3. **Гонка.**
   - **Условие:** лимит — `N` открытых заявок, у A их `N−1`.
   - **Действие:** A отправляет две заявки подряд, не дожидаясь ответа; 1000 повторов.
   - **Ожидаемый результат:** каждый раз принята ровно одна.
4. **Обход через `REPLACE`.**
   - **Условие:** заявка A на пределе лимита объёма.
   - **Действие:** `REPLACE` на лот больше; `REPLACE` с ценой за коридором.
   - **Ожидаемый результат:** оба отклонены, заявка A не изменилась.

**Ограничения и последствия:** фаззинг снижает, но не исключает риск сбойной команды; если она всё же попадёт в журнал, восстановление остановится и потребуется ручной разбор. Фиксированный коридор может остановить и честную торговлю, если рынок действительно ушёл, — тогда коридор сдвигает администратор. Клиент должен хранить счётчик клиентских ID между подключениями. Отказы gateway не попадают в журнал команд и записываются в служебный журнал безопасности.

### <a id="d-03"></a>D-03. Ядро исполняет только то, что уже записано на диск

**Контекст:** если журнал пишется одновременно с исполнением, отчёт о сделке может уйти клиенту раньше, чем команда попадёт на диск. Если биржа упадёт в этот момент, после восстановления сделки не будет, хотя клиент о ней уже знает ([T-06](THREAT_MODEL.md#t-06)). Кроме того, журнал — единственная основа для восстановления и разбора споров, поэтому испорченную или подменённую запись нельзя молча исполнить ([T-07](THREAT_MODEL.md#t-07)).

**Решение:**

1. Порядок обработки: sequencer → журнал → ядро. Журнал записывает пачку команд на диск (`fdatasync`) и только после этого передаёт её ядру.
2. Каждая запись содержит номер, время, участника, роль, команду, контрольную сумму и хеш, связанный с хешем предыдущей записи. Записи образуют цепочку.
3. При восстановлении проверяются контрольные суммы, непрерывность номеров и цепочка хешей. Оборванная последняя запись отбрасывается; любая другая ошибка останавливает запуск с указанием номера испорченной записи.
4. Снапшот хранит номер и хеш последней учтённой записи и сверяется с журналом.
5. Журнал открыт только на дозапись. Чтение журнала администратором тоже записывается в журнал.

**Обоснование:** ядро не видит незаписанных команд, поэтому наружу не может уйти то, чего ещё нет на диске ([SR-07](SECURITY_REQUIREMENTS.md#sr-07)). Контрольная сумма обнаруживает повреждение записи, цепочка хешей — удаление, перестановку и подмену. Мы сравнили два способа обеспечить [SR-07](SECURITY_REQUIREMENTS.md#sr-07):

| | A. Сначала запись, потом исполнение (выбран) | B. Исполнение одновременно с записью, ответы ждут подтверждения записи |
| --- | --- | --- |
| Задержка ответа | Время записи + время исполнения | Большее из двух |
| Что контролировать | Ничего: ядро не опережает диск | Каждый путь наружу: отчёты, публичный поток, снапшоты, ответы на запросы. Один забытый путь нарушает [SR-07](SECURITY_REQUIREMENTS.md#sr-07) |
| Если диск остановился | Торги останавливаются сразу | Торги останавливаются, когда заполнится буфер ответов |

Выбран вариант A: запись на диск идёт намного дольше исполнения, поэтому задержки двух вариантов почти равны, а вариант B требует контролировать каждый путь наружу.

**Связанные угрозы:** [T-06](THREAT_MODEL.md#t-06); также [T-07](THREAT_MODEL.md#t-07).

**Связанные требования:** [SR-07](SECURITY_REQUIREMENTS.md#sr-07); также [SR-08](SECURITY_REQUIREMENTS.md#sr-08).

**Будущая проверка:** критерии приёмки [SR-07](SECURITY_REQUIREMENTS.md#sr-07) и [SR-08](SECURITY_REQUIREMENTS.md#sr-08), а также:

1. **Незаписанное не уходит наружу.**
   - **Условие:** тестовая сборка, в которой журнал останавливается перед записью пачки на диск.
   - **Действие:** клиенты отправляют заявки; процесс биржи принудительно завершается и запускается снова.
   - **Ожидаемый результат:** до сбоя клиенты не получили ни одного ответа по этим заявкам; после восстановления этих заявок нет. Остановка перед записью нужна потому, что принудительное завершение процесса не теряет данные, уже переданные ОС, и без неё тест не отличит «записано на диск» от «передано ОС».
2. **Полученное совпадает с восстановленным.**
   - **Условие:** нагрузка от ботов; клиенты сохраняют все полученные сообщения.
   - **Действие:** 100 раз уронить биржу в случайный момент и восстановить.
   - **Ожидаемый результат:** каждое полученное сообщение совпадает с восстановленным сообщением с тем же номером.
3. **Порча журнала.**
   - **Условие:** копия журнала.
   - **Действие:** изменить байт в середине; удалить запись; переставить две записи; обрезать последнюю запись.
   - **Ожидаемый результат:** в первых трёх случаях восстановление остановлено с номером записи; в последнем запись отброшена, восстановление завершено.

**Ограничения и последствия:** каждый ответ ждёт записи на диск; если диск остановился, останавливаются и торги. Решение работает, только если `fdatasync` действительно сохраняет данные; потерю питания проверки не воспроизводят. Тот, у кого на хосте есть права процесса биржи, может переписать журнал целиком вместе с хешами — это остаточный риск [T-07](THREAT_MODEL.md#t-07). Выбор стоит пересмотреть, если замер покажет, что исполнение пачки занимает столько же времени, сколько её запись, а задержка станет главной метрикой проекта: тогда лучше вариант B.
