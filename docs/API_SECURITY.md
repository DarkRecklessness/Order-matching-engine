# Безопасность API и sequencer к EK1

Документ описывает только границу API и sequencer. Он должен быть включён в
общую модель угроз проекта, а его идентификаторы — связаны с общекомандными
материалами без переименования перед фиксацией EK1.

## Компоненты и граница доверия

```text
недоверенный HTTP-клиент
          |
          | JSON-команда
          v
  [HTTP adapter] -> [CommandApi: валидация] -> [CommandSequencer]
                                                     |
                                                     v
                                        matching engine (заглушка)
                                                     |
                                                     v
                                                WAL (позже)
```

Всё, что пришло по HTTP, считается недоверенным. HTTP adapter не принимает
решений о допустимости торговой команды: он передаёт тело в `CommandApi`.
Только успешно проверенная команда может попасть в `CommandSequencer` и
получить номер. Аутентификация и авторизация пока отсутствуют, поэтому сервер
слушает только loopback-интерфейс и не готов к публикации в сеть.

## Требования безопасности

### SR-01. Отклонение некорректной команды

API должен до изменения состояния отклонять команду с отсутствующими
обязательными полями, неизвестным типом, недопустимой стороной заявки,
неположительной либо не представимой в `int64` ценой или количеством.

**Критерий приёмки:** если клиент отправляет такую команду, API возвращает HTTP
400, команда не передаётся в sequencer, а значение `last_sequence` не
изменяется. После подключения matching engine такая команда также не должна
передаваться ядру.

Связи: [T-01](#t-01-некорректный-ввод) → `SR-01` →
[D-01](#d-01-единая-валидация-до-sequencer).

### SR-02. Единственный порядок принятых команд

Каждая принятая команда должна получить уникальный положительный номер. Номера
должны образовывать единую возрастающую последовательность без дубликатов,
включая конкурентную подачу команд.

**Критерий приёмки:** при конкурентной подаче `N` корректных команд в новый
экземпляр sequencer множество присвоенных номеров равно `{1, ..., N}`.

Связи: [T-02](#t-02-гонка-при-нумерации) → `SR-02` →
[D-02](#d-02-синхронная-точка-сериализации).

### SR-03. Номер только для принятой команды

Отклонённая при проверке команда не должна расходовать номер последовательности.

**Критерий приёмки:** после корректной команды с номером `K` любое число
некорректных запросов оставляет `last_sequence == K`; следующая корректная
команда получает `K + 1`.

Связи: [T-01](#t-01-некорректный-ввод) → `SR-03` →
[D-01](#d-01-единая-валидация-до-sequencer).

### SR-04. Продолжение последовательности после перезапуска

После штатного или аварийного перезапуска sequencer не должен повторно выдавать
номер уже зафиксированной команды.

**Критерий приёмки:** если до остановки была надёжно зафиксирована команда с
номером `K`, после восстановления первая новая корректная команда получает
`K + 1`; незавершённый хвост журнала не применяется как корректная команда.

Связи: [T-03](#t-03-повтор-номера-после-перезапуска) → `SR-04` →
[D-03](#d-03-планируемая-фиксация-последовательности).

## Угрозы и приоритеты

### T-01. Некорректный ввод

Недоверенный клиент передаёт неполную команду, неизвестный тип, отрицательные
значения или число вне диапазона. Если команда будет пронумерована либо
передана ядру до проверки, она может нарушить состояние и создать ложный
разрыв в истории команд.

**Приоритет:** высокий — сценарий доступен любому клиенту и затрагивает
целостность торгового состояния.

### T-02. Гонка при нумерации

Два клиента одновременно передают команды. Небезопасное чтение и изменение
счётчика может выдать одинаковые номера либо нарушить порядок хранения команд.
После подключения ядра появляется дополнительный риск расхождения порядка
назначения номеров и порядка применения команд.

**Приоритет:** высокий — строгий порядок является базовым инвариантом matching
engine; конкурентная подача реалистична для торгового API.

### T-03. Повтор номера после перезапуска

Текущий in-memory sequencer после перезапуска снова начинает с `1`. После
подключения реального matching engine это может сделать журнал неоднозначным и
нарушить восстановление.

**Приоритет:** высокий для рабочей версии. На EK1 угроза закрыта проектным
решением и будущей проверкой, но сам механизм ещё не реализован. До появления
WAL сервер не позиционируется как сохраняющий состояние между запусками.

## Проектные решения

### D-01. Единая валидация до sequencer

Проверка полей выполняется в транспортно-независимом `CommandApi` до вызова
`CommandSequencer::submit`. HTTP adapter отвечает только за HTTP-маршрутизацию.
Так один и тот же порядок «разобрать → проверить → пронумеровать» сохраняется
при тестировании и при возможной замене транспорта.

**Ограничения:** текущий прототип поддерживает только плоский JSON-контракт и
не реализует аутентификацию, авторизацию и ограничение частоты запросов. Эти
ограничения запрещают публикацию сервера во внешнюю сеть.

**Проверка:** текущий автотест отклоняет дробные значения и числа за верхней
границей `int64`, принимает `INT64_MAX` и проверяет, что отклонённые команды не
изменяют `last_sequence`. Таблица негативных API-тестов для всех обязательных
полей, неизвестного типа и недопустимой стороны будет расширена далее.

### D-02. Синхронная точка сериализации

Назначение номера и постановка принятой команды в in-memory историю выполняются
под одним mutex внутри `CommandSequencer::submit`. Это и есть текущая граница
сериализации. При подключении WAL и matching engine граница будет расширена так,
чтобы фиксация и передача команды сохраняли тот же порядок; обработка ошибок
записи будет определена до реализации WAL.

Рассматривался атомарный счётчик: он дешевле и гарантирует уникальные номера, но
сам по себе не упорядочивает добавление команд в историю и их будущее применение
ядром. Mutex выбран потому, что корректность единого порядка важнее пропускной
способности.

**Граница применимости:** решение предполагает один процесс sequencer. При
переходе к нескольким процессам или узлам потребуется внешний источник порядка
либо иной протокол. Выбор следует пересмотреть, если измерения покажут, что
сериализация стала узким местом при требуемой нагрузке.

**Будущая проверка:** многопоточно отправить большое число команд с барьером
старта; подтвердить уникальность и отсутствие разрывов, а после подключения
ядра — совпадение sequence order с порядком фактического применения. Текущий
автотест уже проверяет базовую часть этого свойства на 32 потоках.

### D-03. Планируемая фиксация последовательности

Перед применением команды ядром sequencer будет записывать в append-only WAL
номер, длину записи, сериализованную команду и контрольную сумму. Запись должна
стать устойчивой до изменения in-memory состояния. При запуске sequencer
восстанавливает последнее подтверждённое значение и продолжает с него;
повреждённый или неполный хвост не применяется.

**Статус:** проектное решение для EK1, реализация отложена. Текущий
`CommandSequencer::submit` содержит обозначенную точку будущей интеграции.

**Ограничения:** контрольная сумма обнаруживает случайное повреждение, но не
защищает от намеренной подмены пользователем с доступом на запись. Политика
`fsync`, формат версии и реакция на ошибку диска должны быть уточнены до
реализации.

**Будущая проверка:** после каждой возможной границы записи принудительно
обрывать процесс, перезапускать его и проверять, что восстановлен только
целостный префикс, номера не повторяются, а следующая команда получает номер на
единицу больше последней восстановленной.

## Демонстрационная цепочка

```text
T-02: конкурентные команды могут получить некорректный порядок
→ SR-02: номера уникальны и образуют 1..N
→ D-02: единая mutex-защищённая точка назначения и хранения
→ конкурентный тест нумерации и будущая сверка с порядком применения ядром
```
